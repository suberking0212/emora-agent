## 1. 执行摘要

本报告回答：**如何释放「大模型原生能力」，让 Emora 获得更好的推理与情感支持质量，而不是靠堆砌外部组件。**

核心结论：

1. **「换更大的推理模型」不等于「更好的情感支持」**。arXiv 2603.09997 的临床测量是第一手证据：GPT-4o→o4-mini→GPT-5-mini 三代模型共情得分无统计学显著差异（Kruskal-Wallis H=4.33, p=0.115），真正改变的是「安全姿态」——危机检测单调提升、但建议安全性下降。**原生能力的天花板在「对齐与安全」，不在「共情」**。
2. **推理模型的「原生能力」有明确的使用边界**：OpenAI 官方（2026）已把工具调用与 Structured Outputs/Responses API 深度绑定；GPT-5.4 起 Chat Completions 在 `reasoning_effort != none` 时不支持工具调用；GPT-6 Astra 在 Chat Completions 下完全不能调用函数。**原生能力释放的正确姿势是走 Responses API / `text.format` 结构化输出，而不是继续在旧接口上打补丁。**
3. **「表演式共情」是原生能力的已知反噬**：ICDH 2026（AuthenDia4MH）与 ICDH 2026（Performative Empathy vs Authentic Support）实证：专有推理模型（GPT-4o、Claude）倾向「过度附和、结构僵硬、冗长复杂」的表演式共情，甚至因「复杂度惩罚」而比人类咨询师更不易读；部分开源小模型（Ministral-8B）反而更贴近专业咨询师的简洁自然。
4. **中文安全护栏上，Emora 现用的 Qwen3Guard 是正确选择且有硬证据**：Qwen3Guard 技术报告（arXiv 2510.14276）显示其中文 prompt/response 安全分类 F1 全面优于 Llama Guard 3/4 的中文表现。

**一句话**：课题 B 的正确策略是「**善用原生结构化输出 + reasoning_effort + 原生安全对齐，但警惕表演式共情的反噬，用评测兜底**」——而不是「换更新更强的大模型」。

## 2. 背景与目标

### 2.1 背景

Emora 通过 OpenAI 兼容 SDK（`AsyncOpenAI`）调用模型，当前实现用 `stream=true` + 把 JSON Schema 写进 prompt（`backend/provider.py` 注释明确：该网关文档是「普通 chat completions，非原生 json_schema response_format」）。这实际上**没有用上模型的原生 Structured Outputs / reasoning 能力**。

### 2.2 目标

- 搞清 2026 年 OpenAI 原生能力的真实接口形态与边界；
- 判断哪些原生能力（reasoning、structured outputs、原生安全）能提升 Emora，哪些是陷阱；
- 给出「原生能力释放」的落地建议，且与课题 A（专业知识）和综合报告的评测闭环衔接。

### 2.3 范围与方法

- 只依据 OpenAI 官方文档/官方公告 + 同行评议论文/arXiv 预印本；
- **对 Ruoli（`ruoli.dev`）这类第三方中转的内部上游路由，无公开资料，一律不作结论、不臆测**（本项目 `.env` 曾配置 `api_base=https://ruoli.dev/v1`，诊断记录出现过 `gpt-6.1-sol`/`gpt-6-sol` 等非官方公开命名，均不作为本报告的事实依据）。

## 3. Emora 现状的「原生能力缺口」（只读检查）

| 项 | Emora 现状 | 原生能力 | 缺口 |

| 结构化输出 | JSON Schema 写在 prompt 文本里 | Responses API `text.format` / Chat Completions `response_format=json_schema`（strict） | 未用原生 schema 约束，靠模型自觉 + Pydantic 二次校验 |

## 4. OpenAI 原生能力（2026）事实清单

### 4.1 模型谱系（官方）

| 模型 | 定位 | reasoning.effort | 关键接口 |
|---|---|---|---|
| GPT-6 Astra | 最强（2026-08） | low/medium/high/xhigh/**max** | Responses 支持工具/web_search/file_search/computer use；Chat Completions 不支持函数调用 |
| GPT-6 Sol | 效率（2026-09） | low/medium/high/xhigh | 官方：xhigh 下比低努力 Astra 强、成本更低 |
| GPT-6 Luna | 极低成本 | none/low/medium(默认)/high/xhigh/max | 成本敏感高吞吐 |
| GPT-5.6 Terra / Luna | 上一代 | — | GPT-5.4 起 Chat Completions 工具调用仅 reasoning_effort=none |

来源：[GPT-6 Astra 模型页](https://developers.openai.com/api/docs/models/gpt-6-astra)、[GPT-5.6 Luna 模型页](https://developers.openai.com/api/docs/models/gpt-5.6-luna)、[Introducing GPT-6 Sol and Luna](https://openai.com/index/introducing-gpt-6-sol-and-luna)、[GPT-6 Sol/Luna Oct 2026 更新 PDF](https://cdn.openai.com/pdf/gpt-6-october.pdf)。

### 4.2 关键接口迁移事实（2026）

- OpenAI 官方迁移指南明确指出：**Structured Outputs 在 Responses API 中已从 `response_format` 迁移到 `text.format`**；Chat Completions 保留 `response_format={type:"json_schema", strict:true}`。
- **GPT-5.4 起，Chat Completions 在 reasoning_effort≠none 时不再支持工具调用**；GPT-6 Astra 在 Chat Completions 下**完全不能调用函数**。→ 若 Emora 未来要加工具（PRD 目前排除），必须走 Responses API。
- **Assistants API 已于 2026-08-26 正式下线**（sunset），迁移到 Responses API。
- `verbosity`（low/medium/high/xhigh/max）是 Responses API 引入的输出长度控制，`reasoning_effort`（xhigh/high/medium/low/minimal/none）是通用推理控制。

来源：[Structured Outputs 指南](https://developers.openai.com/api/docs/guides/structured-outputs)、[Responses vs Chat Completions 迁移](https://developers.openai.com/api/docs/guides/responses-vs-chat-completions)、[aifreeapi 决策表](https://www.aifreeapi.com/en/posts/chat-completions-vs-responses-api)。

### 4.3 决策表（针对 Emora）

| 场景 | 建议 | 理由 |
|---|---|---|
| 无工具、纯结构化输出（Emora 现状） | **可暂留 Chat Completions**，但应补 `response_format=json_schema strict` | 官方明示「纯文本或 Structured Outputs 流可继续用，无下线日期」 |
| 需要 reasoning + 工具 | **必须走 Responses API** | GPT-5.4+/GPT-6 限制 |
| 深思考模式（Emora 已有） | 用 `reasoning.effort=high/xhigh` + `verbosity` 控制 | 原生推理深度 |
| 追求成本可控的更强推理 | GPT-6 Sol（xhigh）优于低努力 Astra 且更便宜 | 官方基准 |

## 5. 原生能力的关键实证（与情感支持的交叉）

### 5.1 「共情未变，安全姿态变了」（arXiv 2603.09997，2026-02）

第一手临床测量：3 代 OpenAI 模型（GPT-4o、o4-mini、GPT-5-mini）14 个情感挑战场景、2100 条回复、6 个心理安全维度。

- 共情：三代**无显著差异**（H=4.33, p=0.115）。
- 危机检测：GPT-4o→GPT-5-mini **单调提升**（H=13.88, p=0.001）；自伤场景中，GPT-4o 早期回合危机检测仅 3.6/10，GPT-5-mini 从未低于 7.8。
- 建议安全性：**下降**（H=16.63, p<0.001）。

**含义**：用户感觉「新模型失去了共情」，实为「从谨慎但漏判危机 → 警觉但有时说过头」的权衡转移。**对 Emora：别指望靠换 GPT-6 提升共情；要靠 prompt（课题 A）+ 安全门禁兜住「建议安全性下降」这个新风险。**

### 5.2 「表演式共情 vs 真实支持」（ICDH 2026，AuthenDia4MH）

把心理治疗洞见（情绪一致性、情感动态、语言简洁性）转成可量化指标，对前沿模型 vs 持证咨询师做盲评：

- 专有推理模型（GPT-4o、Claude）呈「**表演式共情**」：过度附和、结构僵硬、冗长，且因「复杂度惩罚」比人类专家显著更难读；
- 部分开源小模型（Ministral-8B）更贴近咨询师的「语言简洁 + 自然措辞」。

**含义**：原生推理能力强，不等于情感支持好；甚至「推理过强 + 冗长」会伤害可读性。**对 Emora：必须用 rubric 约束「简洁性」，并把这条纳入评测（见综合报告）。**

### 5.3 Qwen3Guard 中文 SOTA（arXiv 2510.14276）

- 三档尺寸（0.6B/4B/8B），119 语言，Apache-2.0。
- 中文 prompt/response 安全分类：Qwen3Guard-Gen 全面优于 Llama Guard 3-8B、Llama Guard 4-12B 的中文 F1（例：Chinese Response 平均，Llama Guard 3=62.2、Llama Guard 4=56.5，Qwen3Guard-Gen 显著更高；正文表 4 给出了完整对照）。
- 有 Strict/Loose 两种模式。

**含义**：Emora 现用的 Qwen3Guard-Gen 是中文场景的正确选择，且其技术报告提供了可引用的性能证据，支撑「维持而非替换」。

## 6. 技术方案对比

| 方案 | 描述 | 收益 | 风险/成本 | 结论 |
|---|---|---|---|---|
| 维持 Chat Completions，补 strict json_schema | 给现有请求加 `response_format` | 输出 schema 约束更强、少 JSON 解析失败 | 需改 provider 层 | **推荐（MVP）** |
| 迁 Responses API + text.format | 用最新结构化输出 + reasoning | 面向未来、可加工具 | 改动最大、需重测流式 | 延后（触发：加工具或需 reasoning+工具） |
| 开 reasoning_effort=high/xhigh | 提升深思考质量 | 推理更深 | token 成本↑、可能更冗长 | 深思考模式可试点 |
| 换 GPT-6 Sol/Astra | 更强能力 | 官方基准更优 | 「共情不提升、建议安全性下降」证据 | **不为此目的换**（见 §5.1） |
| 引入原生工具调用 | 加 web/file 检索 | 拓展能力 | PRD 排除；GPT-5.4+ 需 Responses | 不做 |

## 7. 优缺点分析

**原生能力释放的优点**：结构化输出更可靠（strict json_schema 直接减少后置解析失败）；reasoning_effort 可调深度；原生安全对齐随代际增强（危机检测单调提升有证据）。

**原生能力释放的缺点/风险**：
- 建议安全性随代际**下降**（需 Qwen3Guard 输出门禁兜住，这恰好佐证 Emora 现有双门禁设计的必要性）；
- 推理模型「表演式共情 + 冗长」反噬可读性（需 rubric 约束简洁性）；
- 切 Responses API 的迁移成本与流式重测成本；
- 第三方中转（如 ruoli.dev）的上游路由不可见 → 原生能力（reasoning、structured outputs）**是否能真正透传不可验证**，不可作为结论基础。

---

## 8. 对 Emora 的适用性结论

1. **MVP 增量**：为 ChatGPT/OpenAI-兼容请求补 `response_format={"type":"json_schema", strict:true}` 形态的原生结构化输出（对当前 `AsyncOpenAI` 链路是最小改动）；深思考模式试点 `reasoning.effort=high`。
2. **不换模型**：GPT-6 代际不带来共情提升，反而有新安全风险，不作为本课题的「能力释放」手段。
3. **维持 Qwen3Guard**：中文护栏有硬证据，且「原生建议安全性下降」需要它兜底。
4. **不用第三方中转结论**：ruoli 内部上游路由无法公开确认，地址不予采信、不写入事实。

## 9. 架构设计建议（最小侵入）

```
Emora provider 层（backend/provider.py 薄适配）
  Chat Completions 请求
    + response_format = {type:"json_schema", strict:true, schema:<AnalysisDecision/AnalysisResult>}
    + （深思考）reasoning_effort=high
  ↓
  安全门禁不变：Qwen3Guard 输入 + 输出双检查
  ↓
  Pydantic 契约二次校验（兜底，不因原生 schema 而移除）
```

**关键点**：`strict:true` 需要 schema 里所有字段 `required` 且无 `additionalProperties`——Emora 现有 `AgentDecision`/`AnalysisResult` 需核对是否满足（`extra="forbid"` 已具备，但 strict 模式还要求 required 全覆盖，落地时需逐字段对齐）。原生 schema 不是「替代」Pydantic 校验，而是「提前」减少非法输出。

## 10. 实验验证方案

1. **Schema 通过率**：同一批输入下，对比「prompt 内嵌 schema」vs「原生 strict json_schema」的 `provider_invalid_response_shape` / `analysis_unavailable` 错误率。
2. **reasoning_effort 消融**：deep-thinking 模式下，`none/low/high` 三档对「建议具体性」「冗长度」的影响（用 rubric 评分）。
3. **安全回归（关键）**：验证「建议安全性下降」风险是否被 Qwen3Guard 输出门禁挡住；构造一批「用户容易引发过度建议」的输入，确认输出被拦或降级。
4. **简洁性回归**：引入「语言简洁性」rubric（对齐 ICDH 2026 的复杂度惩罚发现），确认增强后不显著变冗长。

**验收标准**：原生 schema 使非法输出率显著下降；reasoning 增强不引入「冗长/表演式共情」；安全门禁对「建议安全性」风险零漏放。

---

## 11. 结论

课题 B 的答案是：**释放原生能力的正确方式，是「用原生结构化输出 + 可调 reasoning_effort」这些确定性接口能力，而不是「换更新的推理模型」。** 因为有硬证据表明：新一代模型的共情并未提升、建议安全性反而下降、且推理过强会带来「表演式共情 + 冗长」反噬。Emora 应在其 OpenAI-兼容链路上补 strict json_schema、试点 reasoning_effort，并用「Qwen3Guard 输出门禁 + 评测 rubric」兜住原生能力带来的新风险。
