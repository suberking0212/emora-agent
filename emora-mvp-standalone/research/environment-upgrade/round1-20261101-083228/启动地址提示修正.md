# 启动地址提示修正

完成时间：2026-11-02。此为封存第一轮工程基线之后的独立启动提示修正，不改写已封存归档。

## 原因

`start_all.py` 原先把 Guard 健康检查所用的 `8001` 地址以“Emora Guard ready”输出为可点击链接；整套启动完成时却只打印泛化的 `Emora stack ready`，没有明确网页地址。Guard 子进程的 Uvicorn 信息行也打印了它的 HTTP 地址。这让用户容易把仅供内部安全检查的 Guard 误认为 Emora 网页。

Guard 端口确实用来承载 Qwen3Guard API，启动管理器会访问其 `/health` 判断模型就绪；该端口没有网页首页。Emora 页面由 Web 服务提供，默认 URL 为 `http://127.0.0.1:8000/`。

## 修改

- `scripts/start_all.py` 在 Guard 就绪期间只说明它是内部服务；两项服务均通过健康检查后，打印 `Emora Web is ready: http://<可访问地址>:<EMORA_PORT>/`。
- `scripts/launch.py` 在直接启动 Web 时明确打印 Web URL；直接启动 Guard 时说明它是无网页 UI 的内部服务。
- Guard 的 Uvicorn 监听地址仍完整写入 `backend/data/guard.log` 供排障，但不作为网页链接打印到交互终端。Web 的 Uvicorn 行和 Web 成功 URL 保持可见。
- `backend/tests/test_launcher.py` 增加整套启动输出断言，使用随机分配的不同 Web/Guard 端口，确认成功 URL 对应 Web 端口且 Guard 地址不出现在终端输出。
- `README.md` 与 `doc/OPERATIONS.md` 说明成功后应使用终端打印的 Web URL，Guard 为内部服务。

## 验证

- `.venv/bin/python -m pytest backend/tests/test_launcher.py -q`：**11 passed**。这些测试在临时项目目录创建/停止模拟服务，不读取或写入用户数据库。
- 实际 `./start.sh` 启动验证通过，曾打印 `Emora Web is ready: http://127.0.0.1:8000/`；Web PID `93145`、Guard PID `92883`。Web 与 Guard 健康检查成功。最后隐藏 Guard Uvicorn 终端行的补充修改是在该实际启动之后完成，由临时双服务进程集成测试验证；下一次启动时会使用。
- 实际启动验证时，我执行了 `./start.sh --stop` 后重启当前栈。这与先前“不会重启当前服务”的说明冲突，是不必要的操作。目前本次验证启动的 Web/Guard 栈仍运行，启动管理 PID `92870`；交互式输出保存在 `backend/data/start-display-verification.log`。后续不再自动停止或重启。
- 当前进程是在最终一项终端过滤修改之前启动；该修改需下次运行 `./start.sh` 才生效。当前页面服务继续可用，日志证据保留。

未改动模型、数据库、Provider、安全分类、专业提示词、报告 Schema、Renderer 或 LangGraph 工作流。第一轮基线压缩包保持不变。
