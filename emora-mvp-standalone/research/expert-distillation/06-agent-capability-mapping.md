# 06 · 专业能力 → AI Agent 能力映射

- 研究日期：2026-10-31
- 目标：把 `05` 的九层能力，映射到让"先进模型真正具备"这些能力的**架构元素**（模型原生推理 / Context / Memory / Skills / Workflow / RAG / 反馈），而非用固定角色 Prompt 模拟。
- 前置约束（来自 `professional-capability/README.md` §2，已复核）：Emora 现状 = FastAPI + LangGraph 1.2.18 单节点 StateGraph + OpenAI 兼容 SDK + Qwen3Guard-Gen + SQLite；**程序控制权与 Agent 决策权严格分离**（Agent 不能自主调工具/写库/发布状态）；无 RAG、无工具、无长期记忆；单轮澄清。

---

## 0. 核心原则：区分"放哪"与"谁来做"

任务书的核心问题是："专业知识放在哪里？哪些交给模型动态推理？哪些要确定性程序？哪些适合 Skill？哪些真要 Workflow？哪些设计会限制模型原生能力？"

**一句话答案**：把"**策略与判断**"交给模型原生推理（Context + 结构化 schema 引导），把"**不可失败的约束**"交给确定性程序（services.py 层），把"**可复用的专业操作**"做成 Skills/节点内指令，**不引入 RAG、不引入多 Agent、不引入 MCP**（无充分证据证明其必要，反而与安全边界冲突）。

## 2. 模型原生推理承担什么（不写死、不模拟）

模型（DeepSeek/现代 LLM）**天然擅长**且应直接承担：

1. **情境理解**（能力 2）：从文本推断"唤起/阻抗/危机/倾诉"态。不要用规则引擎硬分类，让模型读上下文 + 一个带决策条件的 schema 引导。
2. **假设形成与修正**（能力 3）：多假设并存、用反馈修正——这正是 LLM 的 in-context reasoning 强项。
3. **动态决策**（能力 5）："当前该倾听/追问/分析/建议/转介"是一个上下文敏感的生成，不是查表。
4. **共情措辞与反映**（能力 6）：生成"反映意义>重复字面"的复杂反映。

**关键结论**：不要为体现先进性引入 Multi-Agent / MCP / 复杂图。Emora 的单节点 StateGraph 已足够承载"一个同时做归态→假设→决策→输出"的智能体。复杂架构会**限制模型原生能力**（把它切成互相不知情的片段），且与"Agent 不能自助调工具"的安全边界冲突。

---

## 3. Context 提供什么（每轮的必要背景）

Context（system prompt + 当前对话 + schema）提供：

| 内容 | 作用 | 对应能力 |
|---|---|---|
| 能力模型的"条件化决策条件"（浓缩版，如 04 §11 表） | 引导模型在决策分叉点按条件选择 | 2/5 |
| "观察性描述替代诊断标签"的输出规则 | 防止贴标签/诊断 | 1/9 |
| "反映>提问、一次一个有效问题"规则 | 约束提问行为 | 4/6 |
| 当前轮的用户输入 + (若多轮) 上轮反馈 | 反馈适应 | 8 |
| 安全路由的触发条件说明 | 让模型知道何时该"降级"交给程序 | 9 |

**注意**：Context 是"引导"不是"背诵脚本"。把 04/05 的全量表塞进 prompt 会过载；应提炼成**可执行的决策条件**，其余作为 Skills 按需附带。

---

## 4. Memory 支持什么（跨轮次、跨会话连续理解）

当前 Emora 无长期记忆，这对能力 8（反馈适应）与能力 2（情境理解）是**硬缺口**：

- **短期（会话内）**：至少需在单次会话内维护"已识别的情境、已形成的假设、用户已纠正过什么"。这决定"第二句还问不问""换不换假设"。
- **长期（跨会话）**：用户的历史问题类型、已给过的建议、关键关系背景——用于"不要每次从零重建假设"。**但隐私边界必须先行**（见 08）。
- **建议**：MVP 阶段优先做**会话内短期状态**（StateGraph 的 State 字典即可承载），跨会话长期记忆**延期**——因为无隐私合规基线与数据，过早引入会放大风险（与 `two-track-research` 对长期记忆的审慎一致）。

---

## 5. Skills 封装什么（可复用的专业操作）

可复用、可独立升级的专业操作适合做成 Skill（或节点内结构化指令模块）：

1. **`reflect-clarify`**：反映式倾听 + 澄清的范式（何时反映、何时问、反映句式）。
2. **`change-talk-recognition`**：识别用户"ready"信号与阻抗信号，决定建议时机。
3. **`option-based-intervention`**：选项式、可执行下一步的生成范式。
4. **`safety-route`**：危险识别的触发词/信号 + 转介话术 + 资源模板（配合确定性程序，见 §6）。
5. **`non-diagnostic-language`**：把标签翻译为观察性描述的输出规则。

这些是"专业能力"的可复用封装，而非"角色设定"。

---

## 6. Workflow / LangGraph 承载什么（确定性约束）

**唯一真正需要 Workflow 的地方是安全**，其余用模型动态即可。理由：

1. **危险信号 → 转介**必须**确定性**：不能指望模型在长对话里"记得"该转介。用 StateGraph 加一条**前置安全边**：每轮模型输出前/后，由程序检查"是否触发安全信号"（计划+意图+自伤/伤人+明确的精神病性命令），触发则**覆盖**为固定安全路由（直问安全 + 资源 + 转介话术），不进入正常复盘流程。
2. **与现有架构天然契合**：Emora "程序控制权与 Agent 决策权分离"（services.py 固定调用输入/输出门）**正是**这种确定性安全的正确载体——安全路由应做在 services 层，而非 Agent 内部。
3. **单轮澄清上限**：维持现有 `clarification_round` 校验，作为"提问行为"的确定性约束（防止 Agent 无限追问成审讯）。

**结论**：不新增图节点、不引入外部编排。现有 LangGraph 单节点 + 前置安全边即够。

---

## 7. RAG 是否有必要？什么值得检索？

**结论：MVP 阶段不引入 RAG**（与 `professional-capability` 一致，PRD 已把检索列为非目标）。

后续**若**需要检索，值得检索的**不是**"心理学百科"，而是：
- 已核实的安全资源与转介渠道（热线、决定要项的机构）——这是**唯一建议检索的有价值静态知识**，且需"只读+许可+版本过滤"。
- 用户历史会话（那是 Memory 范畴，非 RAG）。

**不建议**检索"疗法知识库"，因为模型原生已能承载这些概念，检索反而引入幻觉源、延迟、且当前无合规引用管线。

---

## 8. 如何利用用户反馈修正模型判断

- 把用户每一句回应作为**信号**注入下一轮 Context（能力 8）。
- 显式要求：当用户以"不是/你没懂/其实"或沉默/绕开回应时，模型应**降级**（从"解释/建议"回到"反映/重新提问"），而非坚持。
- 在评测（见 `07`）中把这些作为**失败类别**去逼模型学会修正。

---

## 9. 规避"机械化"设计（任务书明确要求）

| 要避免 | 为什么伤能力 | 替代 |
|---|---|---|
| 固定分析栏目（情绪/冲突/需求…每轮必须填） | 用户只想倾诉时也被迫"被分析"，违背能力 5 | 栏目**条件化**：只在"用户要分析"时输出 |
| 固定追问数量（每轮必问 N 个） | 成审讯、违背 S11 | 无固定数，一次一个有效问题 |
| 固定建议数量（每次必给 3 条） | 过早给建议、违背 04 §6 | 按"ready"条件决定给不给 |
| 机械化安全免责声明（每轮贴"如有不适请就医"） | 稀释真正危机时的警示，用户在真危机时已麻木 | 免责声明只在**确有危险信号**时出现，且附带具体资源 |

---

## 10. 不要强行引入的架构（避免"为了先进性"）

- **Multi-Agent**：情境/判断/决策本是一体，拆多 Agent 破坏连续性，且与安全边界冲突。❌
- **MCP / 工具调用范式**：Emora 安全模型明确禁止 Agent 自助调工具。❌
- **RAG**：非目标、无合规管线。❌
- **复杂 LangGraph 多节点图**：单节点+前置安全边足够。❌
- **模型微调**：无数据、瓶颈在 prompt+评测（JAMA 结论，`two-track-research` 课题 A）。❌（延期）

**唯一建议的结构性增量**：① 前置安全路由（确定性）；② 会话内状态承接（反馈适应）；③ 提炼后的"条件化决策条件"进入 Context；④ MI 忠诚度 rubric 进评测（承接课题 A）。
