# Emora MVP 第一轮基础工程整改报告

日期：2026-10-31。范围：`emora-mvp-standalone/`。本报告记录工程可靠性整改，不代表专业心理咨询能力验收。

## 1. 结论与验收边界

七项工作的应用侧整改、回归测试和必要的真实调用验证已完成。最终离线测试 **75 passed / 2 skipped / 0 failed**；真实 TCP HTTP 测试完成首次分析、跨轮纠正、SSE 追问、会话隔离、深度模式、Guard 前置拦截和重启恢复。临时测试服务及合成数据库已清理，未打开或迁移现有用户数据库，未重启原有 Web/Guard 进程。

两项上游能力仍有明确限制：

- 当前 `ruoli.dev` 网关未通过严格 JSON Schema 强制约束验证。默认使用实测有效的原生 `json_object`，始终保留完整 JSON 解析和 Pydantic/领域校验；不能宣称严格 Structured Outputs 已贯通。
- `reasoning_effort` 已贯通请求链路，网关接受所有应用档位，也接受非法探针值。无法确认其上游实际生效、被忽略或如何映射，保留原有 `medium` 默认值，不默认升级为高推理。

System Prompt、专业提示内容、`AnalysisResult`/`AgentDecision` 业务设计、两处固定 Renderer、Qwen3Guard 分类实现及 LangGraph 节点/边均保留。新增会话字段属于传输与持久化元数据，不是固定报告 Schema 改造。依赖及锁文件未改；未引入 DeepEval、RAG、微调、长期 Memory 或专业决策流程。

## 5. 持久化、上下文与失败语义

### 5.1 最小数据库迁移

必要性及迁移方案已在 [实施依据](implementation-plan.md) 记录。原 `analyses` 行可保存单次分析与一轮澄清，但不能关联完成后的新追问。只添加：

1. `session_id TEXT`。
2. `turn_index INTEGER NOT NULL DEFAULT 0`。
3. 唯一索引 `analyses_session_turn(session_id, turn_index)`。

`init_db` 幂等检查缺列后添加，旧行 `session_id=id`，每行作为独立会话，不猜测旧对话关系；旧字段与结果保持。澄清继续更新同一行，下一次分析追加新轮。进程内同会话串行化；跨实例根据预期轮次和澄清版本拒绝过期写入，不覆盖已保存结果。这不构成分布式队列或多进程并发压测结论。

临时旧版库已验证迁移、幂等重跑、字段保留、重新打开及冲突处理。本轮真实集成只用合成库。**首次以新版本启动前应停应用并备份实际 SQLite**，备份 API 命令见 [操作手册](../../doc/OPERATIONS.md#会话上下文和数据库迁移)。需要恢复旧版本时停服务并恢复备份；新增列无需破坏性删除。

### 5.2 会话上下文

首次请求省略 `session_id` 创建会话，后续传回该标识；原一轮澄清限制继续存在。完成轮次按顺序构造 user、可选澄清 assistant/user、最终 assistant JSON。每次请求从 SQLite 读取，不依赖进程内聊天缓存，因此可在重启后恢复。失败/拦截记录可在界面回看，不加入后续模型历史。

默认最多 12 个完整历史轮次、32,000 应用字符，计入当前输入和分析提要，优先丢弃完整旧轮次，保留最新连续上下文。当前内容本身超限则 `context_too_long`，不静默丢弃当前输入。该预算不含 System Prompt/消息框架，不等同于 Token 上限；没有摘要记忆或长期 Memory。会话隔离指按 session 查询与传递的工程隔离，不是新增多用户鉴权系统。

前端仅增加 session 传递、同会话侧栏去重、完整历史恢复与新对话清空。`resultText` 和服务端 `_format` 的固定栏目原样保留。会话 API 支持 `next_before` 读取更早页面。

### 5.3 错误与安全

| 类别 | 代表错误 | 处理 |
|---|---|---|
| 网络/HTTP | `provider_transport_error`、`provider_timeout`、`provider_http_error` | failed；不归因于用户内容风险；不自动重试。 |
| 模型拒绝/截断 | `provider_model_refusal`、`provider_incomplete_response` | 显式 refusal/content_filter 单列；截断不继续解析为成功。 |
| JSON/协议 | `provider_json_parse_error`、`provider_invalid_response_shape`、`provider_empty_response`、`provider_protocol_error` | 不修复、不摘取合法片段；失败保持失败。 |
| 应用契约 | `schema_validation_failed`、`domain_validation_failed`、`invalid_analysis_result` | Pydantic、条件业务约束或非空内容未过，不能 completed。 |
| Guard 技术问题 | `safety_check_unavailable` | failed；既不当作 Safe 放行，也不当作已确认风险。 |
| Guard 内容风险 | `unsafe_input`、`unsafe_input_seek_support`、`output_rejected` | 输入阻断或输出不完成，沿用现有 Qwen 分类与求助分支，不判断个人临床状态。 |
| 会话/存储 | `session_conflict`、`session_waiting_clarification`、内部持久化失败 | 冲突显式报告；保存失败不能返回业务 completed。 |

输入 Guard 始终先于分析模型；输出前缀、完整输出和深度提要的安全门继续保留。流式前缀通过对应 Guard 后可能在完整 JSON/Schema 校验结束前显示；后续整体验证失败，不代表此前没有片段显示。只有完整解析、领域校验、整段输出 Guard 和持久化全部成功，才能发布 completed。本轮没有重写该流式协议或 Renderer。

非流式业务失败可能以 HTTP 200 携带 `failed`/`blocked` 状态；SSE 的 HTTP 200 仅代表流已开启。验收检查响应/complete 事件中的业务状态、错误码和数据库结果，不将 HTTP 200 计为分析成功。

### 5.4 日志与隐私

`provider_call.status=parsed` 只说明 JSON 已解析；`analysis_operation` 单列最终应用状态、提要/最终 Schema 与领域校验、调用数及 Provider 错误。请求头 `X-Request-ID` 与 session 关联用于排障。Token 只接收上游实际给出的允许数值字段，包含 usage-only SSE 事件；未提供时为未知。

默认日志不保存用户故事、完整对话、提示词、模型正文或密钥，异常只记录类型和脱敏阶段。SQLite 按原有产品行为保存会话原文，本轮未增加正文日志副本。研究证据仅使用合成输入，保留结论、标识、耗时和用量；对照探针保存的 `HELLO` 为合成格式测试输出。

## 6. Provider 和模型真实验证

### 6.1 环境与证据层级

本机实际配置：OpenAI 兼容 endpoint `https://ruoli.dev/v1`，请求及返回模型标签均为 `gpt-5.6-terra`；本地 Guard 为 `Qwen/Qwen3Guard-Gen-0.6B`。没有切换官方直连账号或其他分析模型，没有把模型标签当作上游身份认证。

`provider-probes.json`、`provider-alternatives.json`、`json-mode-checks.json`、`reasoning-comparison.json` 为真实网关直调，**不经过 Service/Guard/SQLite**。`real-runtime.json` 为真实 TCP HTTP + Provider + Guard + 临时 SQLite。两者与模拟测试分别报告。

### 6.2 原生格式验证

| 实测请求 | 实际结果 | 可得结论 |
|---|---|---|
| Chat strict JSON Schema 与纯文本指令对抗 | HTTP 接受，输出不能通过 JSON/Schema 校验 | 当前网关没有提供可依赖的严格约束保证。 |
| Chat 非法 Schema | 未被拒绝 | 接受参数不代表解析/执行 Schema。 |
| Responses strict/非法 Schema | 两者均接受，输出 `HELLO` | 换到 Responses 也未解决，故不迁移现有 Provider 接口。 |
| Chat 原生产契约的简单样本 | 解析和 Schema 通过 | 单个合法样本不能推翻对抗反例。 |
| 同合成请求，text 与 json_object，各重复 2 次 | text 0/2 为 JSON；json_object 2/2 为 JSON | 默认采用当前网关样本中有效的原生 JSON 模式；样本小，不作总体可靠率保证。 |
| 正式真实 HTTP 场景的 7 次调用 | 7/7 完整解析及应用校验通过 | 当前工程链路已在这些实际场景贯通，不保证所有未来输出。 |

可选 `json_schema` 仅提供正确请求形式，Pydantic 业务字段与 validators 不变。更换 endpoint 或网关升级后需重新运行探针，再决定是否启用严格模式。未实现自动格式降级或静默重试。

### 6.3 推理档位对照

基础探针中 `none/low/medium/high/xhigh/max` 及 `invalid` 均被接受。请求替身检查明确验证参数传递，真实深度请求的两次 Provider 调用均记录 `low`。这些证据可确认发给当前网关的值，无法观察网关发给上游的请求。

另以**相同合成输入、相同现行业务契约**进行 none/medium/high 两轮反向顺序对照；不经过 Guard，不执行专家质量评分：

| reasoning_effort | 第一轮总耗时 ms | 第一轮 total_tokens | 第二轮总耗时 ms | 第二轮 total_tokens |
|---|---:|---:|---:|---:|
| none | 28,157.9 | 5,334 | 11,314.5 | 10,271 |
| medium | 90,644.3，timeout | 未提供 | 10,005.6 | 5,295 |
| high | 12,001.6 | 10,294 | 14,289.7 | 10,359 |

五次成功输出均通过 Schema，包含纠正后的日期和时间；失败一次准确归类 `provider_timeout`。这只验证工程契约与事实更新，不代表建议质量或专业性。相同输入的 prompt_tokens 在约 5k/10k 间变化，none 也有上游报告 reasoning_tokens；结合非法值被接受，不能推断参数确实被执行、被忽略或高档位更好。无稳定的延迟/Token 收益结论，继续使用现有 medium 默认，不新增 Provider 抽象。
