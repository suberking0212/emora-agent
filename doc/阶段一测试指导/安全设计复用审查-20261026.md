# Emora 安全设计复用审查（2026-10-26）

## 结论

状态补充（2026-10-26）：本审查及 [S1](Emora安全分类标准-S1-20261026.md) 保留为设计参考，不构成实现或策略批准。按用户最新指示停止阶段扩展，不继续创建 S2/S3 等文档或扩充 taxonomy/治理规范；生产门禁冻结，不直接放行 uncertain，不引入 NeMo Guardrails 或新的安全模型。当前仅进行现有实现的范围受限复用评估。

本轮是设计/组件审查；没有新增模型调用、跑安全测试集、改生产代码、提示词或门禁。建议现在复用 **MLCommons AILuminate / Safety Taxonomy 的类别定义和判定标准**，用 **Meta Llama Guard 4/3 的 taxonomy、role-aware 输入/输出评估方法和公开样例**作分类器实现参考；评估基准优先考虑经核实可用且授权明确的 AILuminate demo/语言数据加 Emora 端到端人工标注集；中文数据可取得性见后文更正。不要因为参考 Llama Guard 就假设其权重、许可证或中文性能适合直接部署。

现阶段不引入 `nemoguardrails`。先在已有 LangGraph 工作流中把风险识别、任务澄清/完整性判断、策略决策、技术异常与输出安全审查分开建模。将来只有当多类型 rail 编排、流式检查、工具输入/输出检查等需求带来的收益超过依赖与迁移成本，才做小型兼容性试验并决定是否引入框架。

这不是一份已批准的新策略，也不替代产品/安全负责人对下表动作的最终定夺。对不确定风险保留保守安全处置原则，但不得将一般任务含糊、背景不足或分类技术故障伪装成风险命中。

## 一、成熟设计复用与 Emora 映射

Llama Guard 4 对齐 MLCommons hazard taxonomy；其类别说明多以“响应启用、鼓励或认可某类危害”为判据。Guard 的输入模式评估用户消息，输出模式将用户消息和 Agent 回答放入同一对话，并只判定最后一条 Agent 消息。这种 role-aware 方法比关键词命中更适合区分“用户遭到威胁并求助”和“用户请 Agent 帮忙威胁他人”。taxonomy 是风险类别和例子的来源，不会替 Emora 决定用户应收到什么工作流动作。

| Emora 需审查的内容 | 成熟参考 | 复用边界与 Emora 补充 |
| --- | --- | --- |
| 自伤/自杀 | MLCommons suicide & self-harm；Llama Guard S11 | 复用危险协助/鼓励边界。Emora 另需区分当前意图、即时危险、既往经历、第三方风险、引用/转述、社会议题和求助意图；类别命中不等于一律拒绝用户。 |
| 对他人暴力 | MLCommons violent crimes；Llama Guard S1 | 复用暴力协助边界。必须识别行动主体、目标和时间性：受害者求助/脱险与施害者寻求实施方法，处理不同。 |
| 威胁、恐吓、骚扰 | Llama Guard S2 涵盖威胁、恐吓等非暴力犯罪；严重暴力可对应 S1 | 不是所有失礼、冲突或负面表达都构成该类。Emora 需补充目标性伤害/持续骚扰的场景与比例性动作；一般边界冲突应继续帮助表达。 |
| 操纵、胁迫、控制伴侣 | 没有一项 taxonomy 类别能覆盖所有人际操纵；部分威胁/暴力可映射 S1/S2 | Emora 产品非目标明确排除操控、PUA、诱导他人作决定等协助。这是产品行为规则，不应伪称 Llama Guard 的既有 hazard label。应拒绝有害策略，转而提供尊重边界的表达替代。 |
| 非法行为/网络侵入 | MLCommons non-violent crimes；Llama Guard S2 含 cybercrime 等 | 复用违法侵害类别。具体违法与否依赖地域和事实，系统应分类请求是否在促成侵害，不冒充法律判断。 |
| 隐私侵犯/跟踪 | MLCommons privacy violations；Llama Guard S7 | 区分输入披露、请求获取、模型输出泄露、未经授权监视。输入含第三方资料不应自动阻断全部关系分析；应最小化、避免复述/扩散。请求侵入账号、跟踪或套取隐私则拒绝相关协助。 |
| 输入/输出中的其他内容危险 | AILuminate 12 类 hazards；Llama Guard S1–S13/S14 | 按产品范围选择适用类别，不必照搬整个通用模型政策。S14 Code Interpreter Abuse 是工具调用相关；Emora 目前不应为了标签而启用不适用风险。 |
| Prompt injection、隐私泄露、供应链、过度代理、错误输出处理、异常处理 | OWASP GenAI Security 项目 / OWASP Top 10 for LLM Applications | 这是应用/系统安全风险，不是用户危害内容分类。用于架构威胁建模、工具权限、数据流、依赖和日志控制；不能放进一个“安全内容分类器”标签里。 |
| 普通背景缺失、用户目标不明 | Emora PRD 的“必要时短问、先提供有限分析” | 不是 taxonomy 风险。由任务与信息完整性/澄清逻辑负责；即使无法复述完整关系背景，也可以先问用户最需要解决的部分。 |
| 分类服务超时、无效 JSON、schema 错误 | OWASP exceptional conditions 相关的系统可靠性审视；工程错误契约 | 属技术错误，不是 safety_uncertain。应进入显式失败/受控降级路径并记录错误类别，不能让模型故障产生假安全判断。 |

## 二、风险判定和建议处理规则（供评审的草案）

规则分两步：内容分类给出风险类别与证据；Emora 策略再结合意图、角色、当前性、可信度和任务动作，选择处理方式。不要让“检测到某词/类别”直接决定整段用户是否可获得帮助。

| 风险/情境 | 适用条件（初步） | 不应误判的反例 | 建议的策略输出 |
| --- | --- | --- | --- |
| 当前自伤/自杀危险 | 用户表达自己当前自伤/自杀意图、计划、正在实施或急迫危险；或有可信线索显示他人正在遭遇 | 新闻、历史回顾、文学引用、明确非当前意图的讨论、用户替朋友求助（仍需回应支持但非拒绝） | 优先即时安全支持与现实可信援助；如已有迫近信号不等待澄清。不要给方法或普通关系建议替代危机回应。 |
| 自伤主题但非当前危险 | 讨论自伤、自杀议题/往事/担忧，未表明当前意图或计划 | 仅凭“自杀”字样判定正在自杀 | 允许支持性回应；对会实质影响安全处理的当前危险信息做简短、温和的确认；不得给实施方法。 |
| 对他人的暴力/威胁/骚扰请求 | 用户要求写威胁、恐吓、伤害计划、持续骚扰，或请求提高此类行为效果 | 用户报告伴侣威胁自己、求助制定脱离/求援方案；引用对方原话用于分析 | 拒绝有害执行部分，给非暴力且尊重边界的替代；受害者求助进入安全支持与可行选项。 |
| 伴侣操纵/胁迫控制 | 明确要求利用弱点、控制、胁迫、隔离或诱导伴侣违背意愿 | 用户想理解自己是否受控制，或想表达需求、协商边界 | 拒绝控制策略，解释边界并提供诚实表达/安全退出的替代。该类是 Emora 产品规则，需业务定义和评测，不声称是外部 taxonomy 的直接标签。 |
| 非法跟踪、账号/设备侵入、套取信息 | 请求操作步骤、脚本、话术或方案用于未经授权监视、侵入、获取隐私 | 用户求助制止被跟踪、保护账户、记录/报告风险 | 拒绝侵犯协助；提供账户保护、证据保存和现实支持建议。 |
| 隐私暴露 | 用户材料含可识别个人敏感信息，或 Agent 输出会暴露/推断/扩散第三方隐私 | 已去标识的关系事实摘要；用户分享自身材料求一般分析 | 最小化处理、遮盖或不复述敏感值；单独判断是否存在公开/滥用风险，不因含个人信息自动终止全部帮助。 |
| 安全歧义 | 已有具体、可信的风险线索，但关键的主体、对象、当前性/迫近性等仍不能可靠判断 | 单纯缺少项目分工、对话目标、情绪背景，且无风险线索 | 状态应保留为 `safety_uncertain` 概念；依据风险类别做保守支持/必要澄清。明确迫近危险时先安全响应。它不天然等于统一拒绝。 |
| 普通任务不明确 | 用户要做什么、希望 Agent 解决什么问题不明确，且无安全风险线索 | 有风险迹象但把它当普通信息不足 | `needs_clarification` / 普通澄清；可先提供有限帮助，不进入风险拒绝。 |
| 分类技术异常 | 调用超时、网络故障、结构化输出/校验失败 | 模型以合法 schema 返回了风险歧义判断 | `classification_error` / 技术异常，独立处理；是否有限安全降级由明确的运行可用性策略定义，而非伪装成风险分类。 |
| Agent 生成有害建议 | 输出鼓励/促成暴力、威胁、侵犯隐私、操纵等，或在风险情境中建议直接对质/冒险行动 | Agent 在复盘中中性地引用用户原话，且不赞同或扩充 | 独立 output 检查；按违规类别阻止/修订并验证修订，不因 input safe 而跳过。 |

风险判定记录至少需要：taxonomy 版本、风险类别、对话角色（user/assistant/quoted/third-party）、行动意图（求助/陈述/讨论/请求促成行为）、时间性/迫近性（若适用）、证据定位、分类置信/不确定来源、策略动作和规则版本。不得把完整自由文本理由写入脱敏诊断日志；为复核所需的正文证据应在授权的短期安全存储/评审流程处理。

推荐的概念结果模型（只是职责草案，不是要求马上采用此枚举）：

```text
ContentSafetyAssessment:
  verdict: safe | unsafe | safety_ambiguous | null
  categories: taxonomy labels
  target_message_role: user | assistant
  evidence_refs: source-span references
  risk_uncertainty_type: bounded risk ambiguity reason | null

ClassificationTechnicalStatus:
  status: succeeded | classification_error
  error_code: timeout | transport_error | response_invalid | schema_invalid | null
  # On failure, assessment verdict is null; do not invent a safety judgment.

WorkflowDecision:
  action: continue | ordinary_clarification | safety_support | refuse_harmful_assistance | technical_failure
  policy_id: versioned Emora policy
  reason_codes: bounded codes
```

普通任务背景不足由任务澄清独立记录，不放进 risk_uncertainty_type。以上仍是概念草案，不是生产 schema 修改。

评测既看分类表现（逐类 precision/recall、假阳性/假阴性、阈值、拒答表现），也看策略表现（受害者是否获得帮助、危险请求是否被限制、普通用户是否被错误送入拒绝分支、Agent 输出是否带来风险）。安全支持和拒绝有害协助不可合并成同一种“block”。

## 三、现有 post 职责映射

| 设计层 | 当前代码事实 | 审查结论 |
| --- | --- | --- |
| input 风险检查 | `safety.py:classify_text` 固定关键词。pre 命中直接安全回应；未命中再让模型分类 | 只能作窄而可解释的规则信号，存在否定、引用、受害者求助、隐喻、中文变体等上下文边界；不是成熟完整 taxonomy。 |
| pre 模型分类 | `classify_safety(phase="pre")` 只收 context | 输入安全分类职责尚未明示为独立、多标签、role/intent-sensitive assessment；输出 route 与策略绑在一起。 |
| 情境理解 | `understand_context` 生成并校验证据绑定的 ContextUnderstanding | PRD 所需事实理解的一部分；当前 contract 有 claims/evidence/uncertainties，但不保证单独表达用户任务/目标理解。 |
| post 分类 | `classify_safety(phase="post", understanding=...)` 将原文+理解再交同一安全提示，返回同一 SafetyDecision | 名称/提示意图是“再判断安全性”，不是普通完整性检查；但没有定义 post 相对 pre 的新增目的。因同时输入原文和 summary，可能受上下文影响；不能据此认定它有意执行任务澄清。 |
| workflow 决策 | `route_post` 将 safety 与 uncertain 一律路由 `safe_response`，仅 normal 继续分析与必要澄清 | 分类和策略强耦合；安全歧义、目标不清和模型不确定没有独立动作。与 PRD“只有安全风险要求停止普通分析时才仅提供安全回应”存在潜在张力。 |
| 技术异常 | Provider 超时、解码/Schema 失败作为 ProviderError/失败路径 | 与合法 `uncertain` 分开；不要合并。需要另外核验用户可见异常处理，但没有证据显示技术异常映射成 uncertain。 |
| output 安全 | 工作流另有 output `classify_safety` 检查 candidate，最终验证仍在 | 独立检查确实存在，符合输入/输出分开审查的方向；但仍复用同一三值 contract/提示模型，最终分类质量和类别覆盖未在本次审查验证。 |

因此当前 post 可准确描述为：**理解之后的模型安全复核节点；结果同时承担是否停止普通工作流的策略开关。** 它不是完整的任务与信息完整性判断。危险类别、风险证据标准和安全歧义的用户处理未充分定义，且 `uncertain` 与 `safe_response` 绑定造成过度拦截的可能。历史真实 uncertain 的语义原因仍未知。

## API 路线与独立分类器的必要性

上游模型拒绝、供应商过滤、显式 moderation 信号以及 Emora 策略动作是不同能力；OpenAI 官方 [Structured Outputs 指南](https://developers.openai.com/api/docs/guides/structured-outputs) 说明 safety refusal 可被显式识别，但当前适配器使用 OpenAI-compatible Chat Completions，不能假定所有 base_url/模型具有相同信号契约。不能由“通过 API 调用”推断全部已覆盖，也不应默认因此必须自建重复分类。当前适配器支持自定义 base_url，使用 OpenAI 兼容 Chat Completions；静态代码没有显式 moderation 请求，不能由接口兼容性认定供应商安全能力相同。具体端点和模型的保障需独立核实。

设计顺序是：先列 Emora 所需的保护/拒绝/澄清动作，核对上游已提供的能力和可用信号，再以中文端到端评测验证剩余缺口。若上游足以覆盖，不为复用 taxonomy 额外部署 Llama Guard 或叠加通用分类调用。输出安全是独立的评估职责，但可以复用经验证的上游信号，不预设必须独立模型/HTTP 请求。

## 开源组件与许可说明

- **可先复用文字规范和类别，不需要装包或下载模型。** 仍需把源 taxonomy 版本、引用段落、改编差异和 Emora policy version 固化到自己的版本记录。
- **Llama Guard model weights 不能笼统称为 OSI 开源许可。** 具体 Guard 4 使用 Llama 4 Community License 与 AUP；使用、改作或再分发前，应由负责人核对商业条款、归属声明、可接受使用政策和部署/服务形态。Llama Guard 3 各 checkpoint 也应按各自所依赖的 Llama Community License 核查。
- **NeMo Guardrails 框架包为 Apache-2.0**，但通过它拉取/运行的模型、服务和可选 rail 依赖有各自许可证/服务条款，必须逐项审查。
- **AILuminate 公开 demo 数据为 CC BY 4.0**；保留署名和版本信息。官方基准的 practice/private 访问规则与 demo 文件不可混为一谈。
- **中文数据可用性更正**：上述中文支持/语言材料描述不证明公开中文 demo 文件已可取得。2026-10-26 核查的官方仓库公开根目录可见英语、法语 demo CSV；中文入口、具体版本、访问和许可若将来确需使用再核实，不作为已就绪依赖。固定来源与仓库软件/数据许可区别见 S1 §4.1。
- **维护状态以本审查日为准**：NeMo Guardrails 的稳定发行版是 0.24.1，PyPI 标记 Beta 且近期有发布；安全模型本身也必须有 model card、发布版本、推理依赖、资源预算、语言指标和更新/撤回计划。

## 范围受限的成熟方案复用评估（2026-10-26 收敛结论）

本次仅静态核对当前 Provider、分类提示、关键词门禁、路由和安全文案，没有模型调用、CLI 复测、安装或生产变更。既有普通请求 post=uncertain 保留为待解决问题，语义原因未明；不能把它归因于理解错误，也不据此放行。

| 可复用方案 | 对现有问题的适用性 | 本次决定 |
| --- | --- | --- |
| Llama Guard 的角色/意图及输入输出分开判定方法 | 可用于校核现有提示的语义边界，尤其求助、引用与请求实施伤害的区别；没有证据证明能消除当前 uncertain。 | 只作具体提示修订的参考，不部署模型，不重写 taxonomy。 |
| 供应商显式拒绝/过滤信号 | 当前 _structured_attempts 记录 finish_reason，但未单独处理 message.refusal 或 content_filter；空 content/非 JSON 多被归一成 provider_response_invalid。现有接口保留 ProviderError，适合作小范围适配。 | **最小改造候选：仅在实际供应商文档确认当前 Chat Completions 端点的显式 refusal/过滤字段后，在 Provider 解析层先识别该信号，再处理 JSON。** 不把拒绝映射 normal 或 uncertain，不自动重试绕过。 |
| 供应商显式 moderation 能力 | 当前自定义 base_url 的兼容接口不保证有同样能力；未见显式 moderation 请求。上游拒绝不一定提供 Emora 所需的危机/受害者支持信号。 | 不默认新增调用，不替换 pre/post/output。只有具体端点确认支持且已有问题表明必要，才另评替换范围；不因 API 名称兼容就认定已覆盖。 |
| NeMo Guardrails 或新的分类模型 | 无现有证据证明是修复当前具体问题的必要依赖；会增加部署/归因成本。 | 不引入。 |

静态实现还揭示两处独立问题：关键词命中直接进入安全分支，可能对引用、历史主题产生过度分流；safe_message 在没有 self_harm/violence 标记时默认使用“不能帮助跟踪、威胁或操纵”文案，因此仅含 uncertain/空标记的结果也可能收到不匹配的拒绝。这是代码可达性结论，不证明历史日志中用户实际收到该回复。两处均暂不修改：前者涉及门禁，后者涉及用户可见安全策略，应以明确任务另行决定；不借本轮评估顺带改动。

**最小改造建议：先只补供应商拒绝/过滤信号的 Provider 适配；前提是确认实际端点文档和错误契约。** 影响范围限于 providers.py 及必要的错误消费者；保持 SafetyDecision、三值路由、关键词规则、分类提示、工作流和安全文案不变。没有足够上游契约依据时，当前实施范围为零，不猜测 HTTP 错误即安全过滤。

验收只针对拟变更行为：用离线桩响应验证正常结构化 JSON 不受影响、显式拒绝/过滤获得独立错误、超时/schema 错误仍分开、拒绝不重试且不转 normal/uncertain、日志不含拒绝或输入正文；检查现有错误消费者可控呈现且不会持久化伪分析。不追加同类 CLI 验收，也不建立新评测阶段。此建议尚未实施；它改善错误语义，**不会解决或声称解决 post=uncertain**。该问题继续保留，待明确证据支持针对性修改。
