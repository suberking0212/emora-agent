## 结论

真实 Provider 接入**未通过阶段一闭环验收**。认证和结构化探测曾成功，部分模型阶段也成功，但多次完整 CLI 分析未能发布结果。已定位并修正证据提示缺失、连接重试边界、整次调用时限和 schema 错误归类；之后仍观察到模型请求耗时波动及不符合 Pydantic schema 的 UUID 输出。没有绕过证据或结果校验。

本结论区分三个层面：

- 网络/上游：真实调用出现 TLS EOF、`APIConnectionError`、60 秒等待后无响应，以及空 content；其中也有成功响应。因此只能确认链路间歇不稳定，不能仅归因本地网络或供应商。
- 响应契约：真实 `ContextUnderstanding` 曾因中文证据切片错误失败；补充 Unicode 码点、原文精确引用规则后，一次真实理解结果通过校验。真实 `AnalysisCandidate` 曾因 `suggestion_id` 不是 UUID 失败；加入可选 UUID 候选后，这个修复尚未获得成功的完整运行证明。
- 测试方法：早期整链重跑混合了多阶段故障。现在已增加阶段诊断和无网络边界测试，但 provider 稳定性仍不足，故不能标记真实闭环通过。

## 执行结果

- OpenRouter `chat/completions` 直接请求成功过，HTTP 200；隐藏密钥，不记录响应正文。
- Onboard 结构化健康探测返回 `normal`，workspace 配置已保存，Keychain 保存凭据。
- 真实 CLI 运行曾依次成功完成 `pre_safety_gate`、`understand_context`（含证据切片校验）、`safety_gate`，随后分析阶段请求达到 60 秒上限并失败。
- 另一轮分析阶段返回两条建议，但 `suggestion_id` 无法解析为 UUID，触发 schema 错误；无结果发布。
- 加入可选 UUID 候选提示后的运行在首步遇到长时间请求，超过预期的读取等待；据此加入异步整次调用 deadline，并用持续活动的模拟请求验证超时能取消。
- 明确的 JSON 元数据探测有一次成功：`SafetyDecision` 返回合法对象、finish reason 为 `stop`、正文长度 43、没有拒答。模型每次请求完成时间波动较大。
- CLI 负向用例和此前结果照旧；本次代码验证：`ruff check` 通过，默认 pytest 通过（8 passed、5 skipped），启用 PostgreSQL 测试通过（9 passed），compileall 通过。
- 无联网 provider 边界测试覆盖：连接错误最多 2 次；HTTP 400 和 schema 错误不重试；活动请求受整次调用 deadline 限制并被取消。以上只证明客户端行为，不证明服务端稳定性。

## 本次实现调整

- Provider 调用切换为异步客户端并施加可取消的整次调用 deadline；SDK 自动重试关闭，应用层按配置共享有界尝试预算。
- 无效模型 JSON 结构返回单独的 `provider_schema_invalid`，不会误标为连接失败，也不会重试。
- 安全分类提示明确要求 JSON 对象及路由规则；分析提示明确证据引用、中文 Unicode 码点偏移、ID 关联和输出内容约束。
- 每次理解/分析请求提供一组临时 UUID 候选，提示模型从中选择新对象 ID。
- 新运行记录的 prompt 版本为 `prompt.v2`；已完成 run 的快照保持原版本。

## 后续验收门槛
