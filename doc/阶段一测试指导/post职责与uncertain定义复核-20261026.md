# post 职责与 uncertain 定义复核（2026-10-26）

状态：暂停追加分类实验。三条探索性候选理解不升级为正式人工校准基准，不据其修改生产门禁。保留现有测量事实与原始 candidate 标签；本次仅更新诊断判断，不改变产品契约、提示词或代码。

## 产品任务优先

PRD §2、§4、§6 的目标是理解用户的关系经历、情绪困惑与希望解决的问题，区分事实/解释/推断，提供有限但有用的分析和下一步表达建议；缺失信息会实质改变判断或建议时再简短追问。PRD §4 明确“只有安全风险要求停止普通分析时，才仅提供安全回应”。因此输入不完整不能直接等同于安全风险；事实摘要准确也不等同于理解了用户任务。

已有固定职场片段可以暴露代码行为，但没有证明它们代表目标用户的自然表达、情绪困境或端到端任务。压缩参考理解同时改变事实组织、目标表达、引文和未知信息，不能当成更正确的理解。已有计数只是这些探索性样本的分类现象，不构成正式产品误拦截率或理解正确性结论。

## 当前 post 实际契约

| 项目 | 现有实现 / 证据 | 尚缺的定义 |
| --- | --- | --- |
| 调用时机 | `workflow.py:safety_gate`，pre 放行且理解产物通过领域校验后、普通分析之前 | 理解后检查相对 pre 应新增判断什么，未有明确增量标准 |
| 输入 | `phase=post`；context 含当前已确认正文、会话/run/输入版本 ID、澄清计数和允许标记；understanding 含 claims、evidence_refs、uncertainties；candidate=null。当前工作流构造 context 未填 history，其值为默认空列表 | 哪些理解信息与安全决策相关、怎样处理普通背景缺失和假设，不明确 |
| 提示 | pre/post/output 共用 `classify_safety` 提示；只有 output 有额外的候选安全评估说明 | 没有 post 专属决策细则或原文与理解不一致时的优先规则 |
| 输出 | `SafetyDecision` 只有 route（normal/safety/uncertain）与自由字符串列表 risk_flags；结构校验不校验判断是否有语义依据 | 没有强制的风险证据绑定、理由类别或不同不确定性的归属 |
| normal | 提示要求：没有具体安全风险的普通人际/职场分歧使用 normal，risk_flags=[] | 没有明确说明任务意图不清但无风险线索时如何判定 |
| safety | 提示要求：可信危险、自伤、暴力或虐待 | 与有害请求等产品风险范围如何完整对应，仍需核定 |
| uncertain | 原文为 “uncertain when safety cannot be determined” | 未规定需要什么风险线索、怎样区别缺信息/模型判断能力不足，也没有证据门槛 |
| 路由后果 | safety/uncertain 都进 safe_response，不到 analyze_and_advise / clarify_if_needed；normal 才继续 | 门禁执行很明确，但不等于决策语义已经充分定义 |
| 调用故障 | 超时、无效响应、schema 错误抛 ProviderError，工作流失败；不被适配器映射成 uncertain | 模型正常返回 uncertain 是否在表达能力不足，现契约无法识别 |

`ContextUnderstanding.uncertainties` 是未分类的字符串列表，没有将事实未知、目标未知、安全未知分别建模。`SafetyDecision.risk_flags` 的已知代码仅用于诊断白名单，不是强制语义枚举。因此不能从 unknown 风险码推知模型为何返回 uncertain。

还有一个用户体验后果：`safe_message` 只有 self_harm 与 violence 的专门文案，其余默认“不能帮助跟踪、威胁或操纵他人”。普通输入若因 uncertain 且没有上述两类风险码进入该分支，可能收到与其请求不相符的拒绝文案。这是代码路径可推导的风险；旧脱敏日志未保存完整输出，不能声称已核验历史用户实际看到该文案。

## 产生路径与真实原因要分开

已知路径：

```text
当前输入 → pre normal → 理解产物（结构/证据领域校验通过）
→ post 模型响应 route=uncertain → Provider 校验/返回
→ workflow safety_gate 消费 → safe_response → 跳过普通分析与任务澄清
```

历史清单的三条记录证明 Provider 层 post 返回 uncertain，理解领域校验曾通过；早期记录缺少 raw/parsed/provider 的逐次关联与理解正文，不能补成完整上游证据。本轮探索性记录则保存了三值一致性与合成理解快照，可证明客户端收到的 route 一致，不能证明服务端/网关内部判断过程。

**真实原因仍未知。** 未发现确定性代码把普通未知内容转换为 uncertain；也不能证明原理解错误、模型把任务不明确误判成风险，或网关改变了响应。固定 payload 的路由波动仅说明客户端观测到决策变化，不定位随机性、模型配置或网关的具体内部原因。不能恢复被删会话来补这些缺口。

目前能确认的是：定义意图属于安全不确定；流程动作是保守阻断；证据契约不足以验证模型究竟使用了哪种不确定性。不能直接下结论说系统已把三种职责合并，也不能排除实际返回时发生混用。

## 继续实验前需要完成的定义工作

先从产品流程定义三类情况的期望行为，再讨论 schema、提示或策略是否需要改动：

| 情况 | 依据现有产品目标的边界 | 待核定 |
| --- | --- | --- |
| 关系背景或任务目标不完整，无安全风险线索 | 先给有限帮助，必要时询问会改变建议的关键问题 | 什么信息足够开始、什么问题值得追问 |
| 有可信安全线索，但严重性/即时性不清 | 进入安全导向处理，不提供可能增加风险的普通建议 | uncertain 证据条件、应提供何种安全支持及是否澄清 |
| 模型/服务不能可靠完成判断 | 保留显式故障与能力边界，不冒充已确认危险 | 合法响应中的能力不足如何表示、如何对用户解释 |

这些是职责复核的工作项，不是已批准的新门禁。特别需要明确 post 的问题是否为“理解后是否发现原文有依据的安全线索，足以中止普通帮助”，以及它如何与普通澄清协作；现有实现只定义安全分类，未给出上述完整操作标准。

只有职责与预期行为核定后，再设计围绕用户困境的样本：保留事件、关系语境、情绪、请求目标和必要的自然信息缺口，分别评估事实理解、任务理解、帮助/澄清选择、安全处置与建议质量。最小片段保留为组件回归材料，不替代产品评测。当前不继续扩样、不运行消融，也不先决定修改提示词或上下文。
