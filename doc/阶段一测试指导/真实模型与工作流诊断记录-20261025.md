## 完整工作流

使用隔离 PostgreSQL schema `app_diag_20261025`、`checkpoint_diag_20261025` 初始化迁移，并运行完整真实 LangGraph 流程。工作区和默认业务 schema 未用于该次诊断。

- 初始阶段真实调用顺序：输入安全模型判断、情境理解、理解后安全判断、分析、输出安全复核。每次均 HTTP 200、`finish_reason=stop`、Schema 成功且一次尝试。流程用时 88.474 秒；候选结果为 `waiting_clarification`，数据库立即读回 `validated`。
- 实际模型返回了澄清状态，因此按工作流支持的 `SkipResume` 路径恢复，而不是把澄清结果当最终分析。恢复阶段同样执行输入安全判断、情境理解、理解后安全判断、最终分析、输出安全复核。用时 117.851 秒；结果为 `completed`，读回 `kind=final`、`status=validated`。
- 两个阶段都通过真实输出安全复核后才持久化。诊断会话最后执行删除，清理状态 `completed`。
- 随后只读核对 OpenRouter generation 记录：上述 10 次调用均返回 `finish_reason=stop`、`cancelled=false`，路由供应商为 Alibaba；两次分析的服务端 generation_time 分别为 49.132、65.317 秒，与客户端观察一致。
- 本轮真实工作流没有触发拒绝或 provider 异常分支；失败后禁止保存由确定性测试覆盖（`tests/test_workflow_safety.py`）。

## 第二轮诊断：场景与推理预算

使用同一隔离 schema、90 秒超时和单次请求，运行了明确请求、信息不足、重复引用、emoji、较长上下文和安全风险等合成场景。已完成的普通场景都保存为 `initial / validated` 并提出澄清；较长上下文耗时约 139 秒，仍全部调用成功。安全风险场景只执行一次安全路由，保存 `safety / validated`，没有进入普通理解或分析节点。emoji 场景在分析调用期间被人工中断，客户端停止等待后上游结果未知，不能计入成功率，也没有自动重试。

OpenRouter 官方文档说明当前模型支持 `reasoning.max_tokens`，模型目录标记 `supports_max_tokens=true`。诊断级别设置 1024 token 做了两次对照：一次约 12.4 秒但返回 JSON 数组，Schema 失败；一次约 11.9 秒通过 Schema 与领域校验。这个结果说明降低推理预算可能显著降低延迟，但会增加结构化输出风险，不能直接用于生产。原请求仍保留为单次失败，未用重试掩盖问题。

诊断脚本现在记录首 reasoning、首正文、最后 reasoning、总耗时、上游 request ID 和响应顶层形状；测试覆盖 HTTP、传输/超时、流不完整、Schema 根类型错误及敏感信息不落日志。响应正文仍不写入日志。
