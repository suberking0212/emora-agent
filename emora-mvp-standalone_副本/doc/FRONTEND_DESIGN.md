# Emora MVP 前端设计方案

## 1. 设计方向

采用 ChatGPT 用户熟悉的对话工作区：固定侧栏、单一消息列、底部 composer。页面气质安静、直接，主要靠文字层级与严格对齐建立秩序；Emora 深青只用于字标和助手标记，其他区域保持中性。

用户在同一条会话中自由表达；澄清、分析结果、安全响应和错误反馈都在消息流中出现。页面不使用步骤条、分步导航、独立澄清表单或结果跳转页。后端的最多一轮澄清限制由程序执行，不转化为用户可见的流程步骤。

首屏以一句邀请和输入框表达用途，不做营销 Hero。桌面侧栏、顶部标题、消息列、欢迎标题和 composer 共用清楚的对齐轴；对话正文左对齐，用户消息靠右，长文不做两端对齐。空状态不放大型插画或漂浮卡片。

### 设计令牌

| 用途 | 令牌 | 值 |
|---|---|---|
| 页面画布 | Canvas | `#FFFFFF` |
| 侧栏 | Sidebar | `#F8F8F7` |
| 主文字 | Text | `#202123` |
| 次级文字 | Muted | `#686B6E` |
| Emora 深青 | Brand | `#176B64` |
| 键盘焦点 | Focus | `#125F78` |

- 字体：使用平台系统无衬线字体与中文原生字形，不加载外部字体。正文 `16px`、辅助文字 `13px`、标题 `24px`、结果小节 `16px`；字距始终为 `0`，字号不随视口缩放。
- 栅格：桌面侧栏固定 `256px`。主区定义唯一 `720px` 内容轨道；消息列、composer 和顶部标题使用相同轨道宽度与中心线，不各自计算宽度或内边距。窄屏轨道宽度为视口宽度减 `40px`，两侧边距相等。
- 消息：助手消息使用 `28px` 标记列、`14px` 列距和剩余正文列；标记盒与助手名称顶部对齐。用户消息在同一轨道内靠右，右边缘与轨道右边缘重合。
- 侧栏：品牌字标、主操作、历史标题和安全说明共用 `16px` 左边线；品牌字标与侧栏操作使用统一 `44px` 高度的起始行。
- 间距与形状：以 `4px` 为基础、`8px` 为主要节奏。内容使用普通文档流；只有用户消息使用浅灰底，composer 用浅灰底与细边框区分。导航控件圆角 `8px`，用户消息和 composer 圆角 `20px` 以上。
- 品牌：使用 `Emora` 文字字标，不给字母套倾斜路径或临时绘制的图形。助手身份使用同一深青色、固定 `28 × 28px` 的正方形字母标记，字形水平和垂直居中。
- 辅助界面色：消息与 composer `#F4F4F4`，边界线 `#E5E5E5`，悬停底色 `#ECECEC`，焦点 `#125F78`，危险提示使用浅红底与深色文字。
- 原则：只保留一个品牌强调色；用共同轴线、稳定字重和纵向节奏表达精度；不用装饰渐变、营销标签、步骤编号或仪表盘式图表。

### 方案审视

保留用户指定的 ChatGPT 式会话结构，同时修正上一版的粗糙感：品牌只用字标，不再使用不规则对话气泡图形；所有主区元素从同一个 720px 轨道派生，消除消息正文与 composer 的横向错位；侧栏项目共用左边线。分析结果保持文章式层级，浅色中性画布服务于长文阅读。

本方案使用 Anthropic `frontend-design` 技能的领域适配、视觉克制、内容优先和自我审视原则，并遵守 Emora 的产品要求：不生成虚构的情感案例或分析结果，不把 Agent 推测描述成事实。静态预览中的状态说明只用于标示界面结构。

## 2. 布局方案比较

### 方案 A：居中的欢迎页加底部输入

首次打开时把开场语放在主区可用高度的中段，文字左对齐到主内容轨道；composer 固定在主区底部。

```text
┌─────────────┬──────────────────────────────┐
│ 会话导航    │                              │
│             │       开场语                  │
│             │                              │
│             │       composer               │
└─────────────┴──────────────────────────────┘
```

优点是首次使用目标清楚，欢迎内容不会与历史消息竞争；标题左边线与消息正文及 composer 统一，避免居中标题形成额外对齐轴。

### 方案 B：从第一屏开始显示完整对话列

从主区顶部开始显示消息列，空会话时开场语位于列首，composer 固定在底部。

```text
┌─────────────┬──────────────────────────────┐
│ 会话导航    │ 开场语                       │
│             │                              │
│             │ 消息流                       │
│             │ composer                     │
└─────────────┴──────────────────────────────┘
```

布局变化最少，但宽屏空会话会显得偏上，首屏重心不够稳定。

### 选定方案

选择方案 A。空会话时开场语位于主区可用高度中段并左对齐到内容轨道；输入框始终固定在底部。有消息后开场语被消息流取代，主区栅格和 composer 位置不变。欢迎标题、助手正文和结果正文共用轨道的左边线；用户消息靠右并与轨道右边线齐平。长文本不做两端对齐。

本产品的首要任务是让用户自然表达并阅读较长的个人叙述，因此不用表单字段、步骤编号或结果仪表盘组织内容。ChatGPT 式会话骨架符合用户明确指定的交互预期；Emora 的差异放在克制的深青品牌标记、稳定的文章式结果层级和审慎的安全状态表达，不靠装饰性视觉元素制造差异。

## 3. 页面结构

MVP 前后端按代码职责和 JSON API 契约分离，前端使用 Jinja2 应用外壳与原生 HTML/CSS/JavaScript，不建立独立构建工程或独立部署。Jinja2 不渲染业务数据；浏览器通过 `/api/...` 调用后端。生产界面只有会话及历史导航；静态 HTML 预览以只读方式展示界面结构，可通过 URL fragment 查看 `new`、`conversation`、`pending`、`waiting_clarification`、`completed`、`blocked`、`failed` 七种状态。预览不提交输入，也不生成情感分析内容；状态入口不进入产品页面。

### 全局框架

- 左侧会话侧栏采用 ChatGPT 用户熟悉的信息顺序：Emora 标识、“新对话”操作、最近记录列表、底部简短安全边界说明；不放原型状态切换器。
- 桌面侧栏宽约 `256px`；小屏默认收起，通过具名菜单按钮打开，遮罩可关闭，关闭按钮只在侧栏覆盖移动内容时出现。
- 主区顶部使用轻量标题栏；主要空间留给单条会话消息流。
- 桌面顶部标题位于内容轨道左边线；手机端隐藏该标题，只保留轨道左边线处的侧栏菜单按钮，避免标题与菜单形成第二条错位轴线。
- 消息正文使用居中、限宽列，桌面最大宽度约 `720px`；用户消息靠右以浅灰底显示，Emora 回复保持左对齐的纯文本流式排版。
- 主区底部固定对话输入框，随内容自动增高；输入框置于主内容宽度内，底部安全区和滚动空间需为键盘焦点预留。
- 默认空会话在消息区中央显示简短开场提示，输入框始终位于底部；不展示营销 Hero、轮播、推荐语或产品卖点。

### 对话输入与消息流

- 使用 `<textarea>` 作为对话 composer，不用问卷式字段组。视觉标签对读屏器保留，placeholder 只作简短输入提示。
- Enter 发送、Shift+Enter 换行；组合输入期间不得误提交。发送控件使用带可访问名称的向上箭头按钮。
- textarea 随内容增长并设置最大高度，超出后内部滚动；显示与 API 契约一致的长度上限。
- composer 提供默认关闭的原生 checkbox“深度思考”和小字号“思考强度”选择器；选择器由 `/api/runtime` 初始化，显示 Provider 当前模型名及 `none`、`low`、`medium`、`high`、`xhigh`、`max` 六档。两项设置随分析或澄清请求提交，响应和历史记录用于恢复当前记录的实际值。
- 发送后把用户原文作为一条消息追加到当前会话，显示处理中状态；页面不能清空或替换原文。
- 用户消息与 Agent 回复保持单一时间顺序。回复、澄清、分析结果、风险响应和服务错误均不另开页面。
- 键盘和屏幕阅读器状态更新通过单一、上下文明确的 live region 通知，不抢焦点。

### 澄清与补充回答

- 必要时 Agent 在消息流中提出一个澄清问题；用户直接使用同一个底部输入框回答，不出现单独澄清表单或“步骤 2”。
- 补充回答作为新的用户消息追加；当前页面会话中保留原始输入和补充回答，不覆盖原文。当前 `AnalysisResponse` 契约没有返回澄清回答字段，因此重新载入历史时不得假定能恢复该回答；页面只呈现接口实际返回并持久化的字段。
- 回答请求沿用相同安全、长度和服务状态反馈；第二次 Agent 请求澄清属于业务契约错误，显示暂时无法完成的消息，不再追问。

### 分析结果与异常消息

完成结果以一条 Emora 助手回复呈现，回复中按阅读顺序组织：

1. 情境概括；
2. 主要情绪；
3. 核心矛盾；
4. 用户可能在意或需要的内容；
5. 具体建议；
6. 下一步；
7. 必要的安全说明。

结果正文使用易读行宽和舒适行高。建议以编号列表展示，突出具体行动，不用颜色单独表达风险或状态。原始输入属于前面的用户消息，仍可在对话中查看。完成后提供“新对话”操作；MVP 不将无限后续对话作为已承诺能力。

即时危险响应和技术失败也以助手消息内的内联提示呈现。阻断提示说明现实世界求助方向；失败提示解释当前不能完成，并保留会话内容和“新对话”恢复入口。未通过输出检查的模型文本不得显示。

### 历史记录视图

- 侧栏展示最近分析会话的日期、短标题/摘要和状态。
- 标题优先由已保存的概括生成；若没有概括，显示中性日期标题，不拼接或臆造输入内容。
- 点击会话后在主区呈现 `AnalysisResponse` 实际提供的原始输入、澄清问题、结果和状态；不声称能够恢复接口未返回的澄清回答。使用原生链接或按钮语义，键盘可达。
- 空状态说明尚无历史记录，侧栏仍保留“新对话”操作。
- `failed`、`blocked` 和 `waiting_clarification` 与 `completed` 清楚区分，不显示为完成结果。

## 4. 状态与反馈

前端服务状态必须与技术文档中的 API `AnalysisStatus` 一致。`pending` 是同步请求未返回期间的浏览器本地状态，不是 API 或 SQLite 状态：

| 状态 | 页面反馈 |
|---|---|
| `pending`（本地） | SSE 连接期间显示实时处理阶段，深度模式的公开分析提要以小字号显示，并在安全检查后先于正式答复到达；收到终态后提要和运行记录自动折叠。工具/技能事件以小字号逐行列出；当前 Agent 图未注册额外工具或技能。不展示模型私有逐字推理；处理中状态不写入 API 或 SQLite。 |
| `waiting_clarification` | 澄清问题作为助手消息出现，底部 composer 继续用于回答。 |
| `completed` | 完整分析作为助手回复显示，并提供新对话操作。 |
| `blocked` | 停止普通分析，在助手消息中显示简明关切表达和现实世界求助方向。 |
| `failed` | 在助手消息中显示暂时无法完成的说明和新对话恢复操作；保留已有会话内容。 |

输入长度错误显示在 composer 附近，并由 `aria-describedby` 关联。异步结果、发送状态和错误通过单一、上下文明确的 `role="status"`、`aria-live="polite"` 或 `role="alert"` 告知辅助技术，不在每次消息更新时移动焦点。

安全阻断提示不使用威胁性语气，不展示未通过输出检查的模型文本。紧急支持文案由程序定义并受产品安全审阅，不由未验证的候选分析替代。

## 5. 视觉与组件规范

### 颜色令牌

采用 ChatGPT 用户熟悉的浅色中性会话画布：白色主区、近白侧栏、浅灰用户消息和 composer。Emora 深青只作为品牌强调色，不用浅青绿铺满页面。普通文字目标至少 `4.5:1`。

```css
:root {
  --canvas: #ffffff;
  --sidebar: #f8f8f7;
  --surface: #ffffff;
  --surface-soft: #f4f4f4;
  --surface-hover: #ececec;
  --text: #202123;
  --muted: #686b6e;
  --line: #e5e5e5;
  --brand-soft: #e8f1ee;
  --color-primary: #176b64;
  --color-primary-hover: #125a54;
  --danger: #a52b2b;
  --danger-soft: #fff5f4;
  --focus: #125f78;
}
```

页面主体保持纯白，侧栏使用中性灰白，用户消息和 composer 使用浅灰；Emora 深青用于品牌标识，蓝青色用于键盘焦点，深灰用于启用的发送按钮。危险提示用克制的浅红底和深色文字。状态必须同时配文字标签，不只依赖颜色。第一版只做浅色主题，不增加主题切换。

按 WCAG 相对亮度公式核算的主要文字组合：正文 `#202123` / 白底为 `16.11:1`；次级文字 `#686b6e` / 白底为 `5.36:1`；白色品牌标识文字 / 深青 `#176b64` 为 `6.32:1`；危险提示文字 `#5c3232` / 浅红底 `#fff5f4` 为 `10.02:1`。这些色值后续如有调整，仍需重新核验实际组合。

### 字体和排版

使用系统字体，优先中文平台原生字形：

```css
font-family: -apple-system, BlinkMacSystemFont, "PingFang SC", "Microsoft YaHei",
             "Noto Sans CJK SC", sans-serif;
```

建议字号：正文 `16px`，辅助文字 `14px`，页面标题 `24px`，结果小节标题 `18px`。正文行高 `1.6` 左右；结果正文最大行宽约 `68ch`。页面标题和正文使用 `letter-spacing: 0`，不随视口缩放字号。长文本优先换行，不截断核心建议。

### 间距、边框和阴影

- 使用 `4px` 基础、`8px` 主节奏：按钮内边距、消息间隔和结果小节分别使用一致档位；主要消息列和 composer 左右边缘严格对齐。
- 结果区块采用标题、正文、列表和纵向留白组织；只为风险提示、失败提示等需要辨识的状态使用边界容器，避免嵌套卡片和统一卡片网格。
- 侧栏按钮和提示使用 `7–9px` 小圆角；对话 composer 与用户消息使用较大的圆角，匹配熟悉的聊天界面形态。
- 阴影仅用于必要的浮层；页面主体靠间距和边界组织，不靠阴影堆叠。

## 6. 交互与可访问性

- 原生语义优先：`header`、`nav`、`main`、会话消息容器、`label`、`textarea`、`button`、`ol`、`section`。
- composer 的无障碍名称通过关联标签提供；placeholder 只用于简短输入提示，不代替无障碍名称。
- 键盘 Tab 顺序与视觉顺序一致；所有交互控件有明显且不被遮挡的 `:focus-visible` 样式。
- 发送按钮、图标按钮、侧栏导航和新对话操作触控目标至少 `44 × 44px`；控件之间保留足够间距。
- 处理中禁用重复提交，保留明确文本状态；失败信息说明下一步可执行操作。
- 动效只使用轻量颜色/透明度反馈，通常 `150–220ms`；不使用滚动触发、视差、轮播或 GSAP。
- 尊重 `prefers-reduced-motion: reduce`，减少动效时不丢失任何状态反馈。
- 设置 viewport meta，不禁用缩放；窄屏不产生横向滚动。
- 图标如有使用，采用单一 SVG 图标集；装饰图标对辅助技术隐藏，单独图标按钮必须有可访问名称。首版优先使用带文本的按钮，避免不必要的图标依赖。

## 7. 响应式布局

- 手机默认隐藏侧栏；菜单按钮打开覆盖式会话栏。主消息列和 composer 共用视口宽度减 `40px` 的轨道，即左右各 `20px` 边距。
- 平板保留单一主列，适度增加横向留白。
- 桌面采用固定宽度会话侧栏和单一对话主区；历史记录不在主区另占窄栏，消息和 composer 保持一致的居中行宽。
- 预览在 `760px` 切换移动侧栏，在 `420px` 收紧 composer 左边距；生产实现可按容器实际空间调整，不绑定特定设备型号。
- 在 `375px` 窄屏、平板宽度、桌面宽度和横屏方向检查长输入、错误信息、长建议和按钮布局。

## 8. 与技术设计的映射

- `frontend/templates/index.html`：不含业务数据的应用外壳，加载静态前端资源；运行时页面结构和状态由浏览器端维护。
- `frontend/static/styles.css`：颜色、排版、间距、焦点、响应式和减少动效规则。
- `frontend/static/app.js`：通过 JSON API/SSE 调用分析、澄清、运行时和历史接口，传递 `deep_thinking/reasoning_effort`，显示 Provider 模型名，渲染 `AnalysisStatus`，处理本地请求中、错误和完成状态；不依赖后端模板变量，不重写安全判断或 Agent 流程。
- `backend/contracts.py`：后端定义 `AnalysisRequest.text/deep_thinking/reasoning_effort`、`ClarificationRequest.answer/deep_thinking?/reasoning_effort?`、`AnalysisResponse.deep_thinking/reasoning_effort`、`RuntimeInfoResponse`、`AnalysisListResponse` 与 `AnalysisStatus`；前端依据同一 HTTP JSON 字段契约通信，不直接导入 Python 模块。

设计不得新增前端框架、CSS 框架或图标依赖。交互只调用技术设计登记的路由；`GET /api/runtime` 用于读取当前模型名和可用推理档位，不新增分析或澄清业务接口。

## 9. 实现验收要点

以下项目用于后续真实前端实现的视觉和可用性验收，不属于 pytest 的自动化产品测试：

- 首页打开即显示对话输入框，而不是介绍页或表单步骤；
- 用户可在同一消息流自由输入，澄清、完成、阻断和失败均表现为对话消息；
- 用户补充时，原始描述仍保留在同一会话；
- 输入超限和请求失败时内容不丢失，composer 明确反馈状态；
- 键盘可完成导航、输入、提交和历史记录打开；
- 字段错误有文字说明并可由辅助技术感知；
- 小屏无横向滚动，长文本和长标题不遮挡相邻内容；
- 普通文字对比度达到 `4.5:1`，焦点清晰可见；
- 用户偏好减少动效时，状态和操作反馈仍完整。
